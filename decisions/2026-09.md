## #1 (2026-09-02)
- 场景: CSGK SAP 仓库库存报表 (SAP STORAGE SG.txt) 由 8 列更新为 13 列,讨论新增列与现有 JSONB 列的处理
- 决策: 新增 5 列 (MTyp / Matl Group / MRPCn / S / Stck no.) 成为正式 typed 列,显示在仓储原始数据网格且可筛选/排序;同时把现有存在 JSONB 里的 5 列 (Material Description / BUn / Description / Qual.Insp.) 与新增 Blocked 一并升级为正式列;source_values 仍保存全部原始键作保真
- 理由: "都有考虑" — 既为将来筛选/排序/出报表,也为数据维护整洁,不让数据散在 JSON 里
- DNA 原则: 进入用户可筛选/排序/出报表的数据必须是真实列;JSONB 保留原始源值作保真层,但不承担查询职责
- 标签: engineering

## #2 (2026-09-07)
- 场景: 虚拟 Plant 领域建模 (3079 无货值仓 / 未来三角贸易)。讨论「虚拟」这件事怎么在模型里表达
- 决策: 选显式类型枚举 (`plant_type`),否掉了 agent 推荐的「不分类型、用可覆盖的继承吸收差异」(理由是枚举值要跨后端/前端/i18n 三层维护,成本长期)。同一轮里反向砍掉 `is_virtual` 布尔,让「是否虚拟」降为类型的派生属性
- 理由: "两个不同类型的 Plant, 显示的功能是不一样的" — 无货值仓只关注 Storage, 三角贸易只关注 Trading
- DNA 原则: 一个分类如果会决定用户看到什么,它必须是显式声明的一等概念,不能靠「某个字段填没填」推断出来。推断可以描述现状,不能承载契约 —— 别人要照着它做决定时,它必须是被声明的,不是被算出来的。反过来,一个不决定任何东西的分类不配拥有字段
- 标签: mental-model

## #4 (2026-09-23)
- 场景: 设备 (Device) 纳入版本管理以支撑成本分析。设备的原值/折旧年限/功率/占地/归属只有当前值,导致历史报表里人工费、电费、分摊都是当时口径,唯独设备折旧按今天算。讨论「这台设备在某个历史日期算不算数」怎么表达
- 决策: 否掉 agent 设计的两套日期 —— 成本配置的生效区间 + 设备自己的在役起止 (两个新字段)。改为只留一套: 设备是否纳入某日期的计算,完全由「当时有没有可用的成本配置覆盖」决定。设备本身不建生命周期字段;`manufacture_year` 保持纯记录用途,不参与任何计算。同一轮里也否掉了 agent 提的三个存量回填选项 —— 那个问题在新框架下不存在
- 理由: "实际是否要把该设备纳入计算还是看当时是否有可用的报价/成本相关配置. 这样只用考虑一套机制就行, 不必同时考虑配置版本与设备本身的字段"
- DNA 原则: 一个实体「是否参与计算」若能由既有配置的覆盖关系推出,就不要再给实体本身加一套生命周期字段。两套必须永远保持一致、却没有任何机制强制一致的时间维度,一定会漂移,且漂移之后无法判定谁对 —— 多记一个维度看起来更忠实于现实,实际买到的是一个无人维护的第二事实源。系统只承诺它能验证的事实;纯记录性字段不得被提升为计算依据
- 标签: mental-model

## #5 (2026-09-23)
- 场景: 同 #4,设备成本版本化的实施过程中。ADR 写的是七个成本/归属属性搬进版本子表、设备行只留身份信息,但 coordinator 在派牌的 Issue 正文里加了一句「device 表上的原列本次不删 —— 降级路径要走得通,删列单独一张牌」,与自己写的 ADR 相矛盾。实施者按 Issue 做,于是同一组数字存了两份
- 决策: 否掉「保留原列 + 同步机制」。七个字段只存在于版本表,设备行上删除,不留第二份。降级靠迁移自己写回(重建列 + 从最新覆盖版本取值),不靠保留副本
- 理由: "只应该存在于设备版本中, 设备基础信息中不应该存. 不需要存两处还要搞同步这种机制"
- 实测代价(这是被证伪的一侧,不要删): 保留两份的那一版真的实现出来了,为了让两份对上挂了 ORM after_update 监听器,而它的 UPDATE 没有版本限定,把设备的**全部历史版本**用当前值覆盖;豁免开关全仓只设了一处,于是「停用设备」「恢复设备」两条路径会抹掉该设备的成本历史。4319 个用例全绿,没有一个发现 —— 因为监听器本来就是为了让已有测试通过才加的。同一版里新建设备的生效日期被写死 2000-01-01,使得今天录入的设备出现在去年的成本里,正好废掉整个 ADR 的意义
- DNA 原则: 这是 P2 的一次应用,不另立原则。补充一条可判定的推论: **同一事实存两处,必然要长出一个同步机制;而同步机制的失败面大于它规避的迁移风险。** 同步机制的豁免开关是把不变量押在「下一个写调用点的人记得设」上,他不会知道它存在。判据: 当你发现自己在设计「怎么让 A 和 B 保持一致」时,先问为什么有两份
- 标签: mental-model

## #6 (2026-09-23)
- 场景: 设备组 (Device Group) 的版本管理。调研发现「设备属于哪个组」已经按生效日期记在每台设备的成本版本里 (ADR-114 刚合并),缺的只是从组这一侧看和改的入口。agent 推荐: 记录留在设备上,设备组页面只做一个视图
- 决策: 否掉 agent 的推荐。把组成员从设备身上摘出来,改由设备组维护、按版本记;设备那边只能看。为此推翻了一天前刚合并的 ADR-114 的一部分 (ADR-115)
- 理由: "实际这个信息应该属于Device Group. 是属于Device Group(模块/领域)来维护的. 不该由Device来维护及做版本维护"
- DNA 原则: 一条信息应该放在负责它的那一方,而不是放在碰巧存得下它的地方。「数据已经在那儿、改动最小」不能成为让它留在错误一方的理由;在两侧各做一个视图,代替不了把它交给真正负责的一方。这是 P8 的一次应用:谁来维护,决定它住在哪
- 标签: mental-model

## #7 (2026-09-25)
- 场景: 调研 Cost 模块哪些输入缺日期段版本。发现 ADR-114 定了要版本化的设备折旧年限、功率、占地面积、主设备标记,在 2026-09-24 又被挪回设备行、按当前值读取;agent 把这报成「过去日期的报价用今天的年限/功率算」的缺口
- 决策: 不是问题,这四项不加版本。原值继续按日期记版本
- 理由: "原值会每年根据通货膨胀率进行调整…而年限是法律规定的, 不会变的. 功率也与占地面积也一样. 功率机器制造出来就已经定了. 占地面积是投影面积, 也是机器的固有属性"
- DNA 原则: 一个属性要不要记历史,看它在现实里会不会变,不看它影响不影响结果。固有的、法定的属性只有一个值;给它记版本等于在模型里制造现实中不存在的「变化」,还凭空多出一份要维护、会出错的数据。「凡是进入计算的都版本化」这种建模上的整齐,让位于对现实变化结构的忠实
- 当前决策如何体现它: 面积片归属会随管理调整而变 → 记版本(#512);机器出厂即定的参数 → 不记;真正随时间变的是价值,由原值版本 + 通胀率承载
- 标签: mental-model

- 当前决策如何体现它: 颜色当主体、数字弱化;单行趋势按需点开;只保留「超过 100%」一条硬线,不给读者多加要解读的门槛。是 P5「可见元素服务决策」在展示密度上的延伸

## #9 (2026-09-29)
- 场景: 后台任务管理页 (#408/ADR-124)。agent 原有实现只有一列 health 汇总「正常/失败/漏跑/已停止」,「上次成功时间」当成功信号;新加的「立即运行」返回 202「已投递」,于是页面上「成功」既可能指投递成功也可能指执行成功,运维分不清
- 决策: 拆成两列——「健康状态」(调度/系统层:正常/失败/漏跑/已停止/还没跑过) 与「执行状态」(最近一次运行的结局:还没跑过/运行中/成功/失败);并钉死 Last Success 只在任务函数返回后计,投递/触发不算成功
- 理由: "这个任务管理要显示任务本身健康状态与任务执行状态. 而且 Last Success 要以任务执行完成来计."
- 深层张力: 运维想一眼看到「任务有没有被跑到」的乐观信号 vs 状态必须如实反映结果,不能把「已投递/已调度」伪装成「已成功」
- DNA 原则: 状态展示把「调度/触达」与「实际结果」分成两个层面;成功只由实际完成定义,投递或计划本身不计成功
- 当前决策如何体现它: health(调度/系统) 与 execution(运行结局) 两列并排;`last_success_at` 仅在 runner 的 job() 返回后落 `finished_at`;已开始未结束的实例读作 running 而非 succeeded
- 标签: product-ux

## #10 (2026-09-29)
- 场景: Spec 成为成本与产能核算单位 (#576)。Spec 的工位数 / 每工位人数 / 总面积要按日期记版本;没配时可由绑定机器推算。agent 推荐「逐项配置、空的那项在计算时按机器推算」
- 决策: 否掉逐项推算,改为三项整套进同一个日期版本;填写时用机器信息预填;某天无版本才整体按机器推算
- 理由: "因为这个也要做时间段版本管理. 一起总体设置才合理. 但填的时候可以使用机器信息预填"
- 深层张力: 计算时自动跟随最新数据的便利 vs 每一天的设置是一份完整、稳定、可追溯的记录
- DNA 原则: 一份按日期生效的配置必须自身完整,不允许一部分是人填的、一部分在计算时临时推出来;便利放在录入时(预填),不放在计算时(补推)
- 当前决策如何体现它: 版本三项必填、同一生效日;预填来自机器;无覆盖版本时三项一起推算,不存在「半套配置 + 半套推算」的一天
- 标签: mental-model
