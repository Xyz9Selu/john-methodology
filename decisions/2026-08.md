# Decisions 2026-08

## #1 (2026-08-05)
- 场景: C-30 高级 Column Filter 的操作符集合范围 — 全做还是先砍
- 决策: 按 RAW 全做 Text/Number/Date 操作符,而非分批
- 理由: 后端 gt/gte/lt/lte/range 已全部实现,前端加 UI 的成本是边际的;分两次做反而要改两遍 UI 和 e2e
- 标签: engineering

## #2 (2026-08-05)
- 场景: Number/Date 列有了操作符 UI 后,和现有"搜索+多值勾选"的关系
- 决策: 替换 — number/date 列不再以勾选离散值为主要交互,走操作符路径
- 理由: 对 number/date 列勾选离散值本身价值低(用户不会去勾几百个数值);并存/双 tab 会引入"同一列两套条件怎么合并"的复杂语义
- 标签: product-ux

## #3 (2026-08-05)
- 场景: 高级 Column Filter 的菜单布局 — 双 tab 还是单视图
- 决策: 单视图 — 条件规则编辑器与筛选选项列表同屏可见,不做 tab 切换
- 理由: 同一个视图下能同时看到条件与筛选出来的选项列表,操作直觉要更顺
- 标签: product-ux

## #4 (2026-08-05)
- 场景: "多条规则 and/or 联立"的支持边界
- 决策: 同列多规则 + 组内 and/or;跨列保持 AND;不做多级嵌套聚合规则
- 理由: 平铺模型一致(条件数组+组合子);支持最常见需求(同列 or、跨列 and)但明确拒绝多级聚合的复杂度
- 标签: mental-model

## #5 (2026-08-05)
- 场景: 记录决策方法论的 skill 应该存在哪
- 决策: 独立全局 skill (john-methodology),非项目内文件
- 理由: 这是个人品味而非某个项目的特性,跨项目复用价值更高;做成 skill 可按需加载,不占每会话上下文
- 标签: mental-model

## #6 (2026-08-05)
- 场景: 方法论 skill 的归纳(principles)触发方式
- 决策: AI 提议,用户点头后才执行;不自动运行
- 理由: 归纳是提炼个人思维的过程,时机和方向应由用户掌控,避免 AI 自作主张
- 标签: mental-model

## #7 (2026-08-05)
- 场景: 方法论 skill 的捕获方式 — 讨论中何时打断
- 决策: 静默积累,会话自然节点统一列确认卡片;不在讨论中途打断问"要不要记"
- 理由: 不打断沉浸的讨论流;批量确认让用户在完整语境下决定取舍
- 标签: product-ux

## #8 (2026-08-05)
- 场景: 合规/规则类约束 (OT cap 等) 是硬拦截还是仅警示
- 决策: 仅警示 + 留余量供人介入,不硬阻断 — 但附条件: 存在最终业务系统 (外部) 做终审,且本系统规则无法与最终规则完全一致 (信息因素、成本因素) 时才适用
- 理由: 硬拦截与批量审批/事后实算冲突,且阻断正当工作;有外部终审兜底时,本系统只需忠实呈现合规现状 (警示/报表),把决策权和风险留给人和终审系统
- 标签: product-ux
- 来源: ADR-036; 条件由 John 2026-08-05 补充

## #9 (2026-08-05)
- 场景: 刚上线的可配置复杂模型是否保留
- 决策: 若复杂度的产出不体现在用户可见结果上,几天后也敢推翻自己的模型,接受小的公平/精度损失换简单
- 理由: 报销 category→group→priority-chain+pool 模型上线后砍成 account-direct;中间年加入者不按比例 — "换取一个简单得多的模型"
- 标签: mental-model
- 来源: ADR-045

## #10 (2026-08-05)
- 场景: 同一概念存在多份可漂移的副本时
- 决策: 只保留一个事实来源;删旧模型/旧列,不建兼容桥;数据缺失时显式失败,绝不静默回退到猜测值
- 理由: 快照列+历史是双源会漂移;无 primary CC 就不提供该能力,汇率缺月不回落旧月 — "静默回退就是数据说谎"
- 标签: engineering
- 来源: ADR-047; exchange-rates spec

## #11 (2026-08-05)
- 场景: 是否为一个新状态/属性建模前
- 决策: 先用真实数据验证底层信号有区分度,再建模;无区分度就砍,且不从粗粒度历史推断更细状态
- 理由: Not Received 状态因 17,681 行 material_receiving 全 NULL 被砍 — 建在恒空信号上的状态无区分能力
- 标签: experience
- 来源: wo-status-rename spec

## #12 (2026-08-05)
- 场景: 值集未知/开放的主数据录入
- 决策: UI 收集不规定 — 自由输入 + 松散约束,不发明固定枚举去卡真实域
- 理由: "允许的值集未知"(不同工厂/ERP 用枚举外值),下拉/枚举会卡住合法主数据录入
- 标签: product-ux
- 来源: ADR-024

## #13 (2026-08-05)
- 场景: 界面上每个可见元素的价值判断
- 决策: 每个可见元素必须支持用户的一个决策;否则移除 — UUID/PK 不上 UI,展示业务可读标识;隐藏用户无动作可做的内部状态
- 理由: UUID 对端用户零含义且"训练用户忽略整列";单级审批的自批内部步骤不暴露给提交者
- 标签: product-ux
- 来源: ADR-019; ADR-033

## #14 (2026-08-05)
- 场景: 事故教训如何写成规则
- 决策: 写成带阈值的、作用域明确的护栏 + 逃生口,而非通用强制令 — 避免把每个无关改动都变成性能项目
- 理由: CSGK 导入曾冻结全站 (健康检查超时);修复规则必须既能防复发又不成噪音 (如 CPU>2s / 嵌套全表扫>2000 行)
- 标签: engineering
- 来源: ADR-062

## #15 (2026-08-05)
- 场景: 是否引入流程/工作流引擎等机制
- 决策: 用能覆盖真实用例的最简构造;机制 (引擎/框架/范围抽象) 留到具体需求出现
- 理由: 审批引擎 (Camunda/Temporal/DSL) 对 HR 规模是过度设计;每类型硬编码短链覆盖一切真实场景
- 标签: engineering
- 来源: ADR-011

## #16 (2026-08-05)
- 场景: 新概念出现时先查是否已有实体
- 决策: 复用既有实体 + 加视图,不新建表/实体
- 理由: 生产 Tag Board 区就是 user_tag 行渲染成看板列,避免新表破坏与 Users 列表标签过滤的对等
- 标签: engineering
- 来源: ADR-051

## #17 (2026-08-05)
- 场景: 两个概念是否该合并
- 决策: 不同维护者、不同变更频率 → 独立维度,别因形似而合并;同一 flag 不承担两种不相关语义
- 理由: 合并 CostCenter 的 name 与 Department 后因 Finance/HR 分头维护而回退;"禁用"复用会与全局退役/恢复语义碰撞
- 标签: mental-model
- 来源: ADR-021; ADR-060

## #18 (2026-08-05)
- 场景: 多个模块出现相似工作流时是否抽象
- 决策: 复制经过验证的模式到第三处仍不算坏味道;抽象要等重复真实开始贵过抽象
- 理由: OT/Reimb 照搬 Leave 的 withdrawn→edit→resubmit 模式,本轮明确不建抽象层
- 标签: experience
- 来源: withdrawn-request-edit-resubmit spec

## #19 (2026-08-05)
- 场景: 更简单的概念取代复杂概念后
- 决策: 删除旧机制本身,不保留兼容层/基线概念
- 理由: 显式 file ids 取代源基线扫描后,删掉整个 baseline 概念 (字段/API/自动采用/快照匹配分支),不叠兼容层保留旧复杂度
- 标签: mental-model
- 来源: source-file-ids spec

## #20 (2026-08-05)
- 场景: 产品讨论中表达 UI 交互原则 (未触发捕获,手动补录)
- 决策: 表格交互以 Google Sheet 为基准 — 操作逻辑、用户直觉尽量统一,让用户直接上手就能操作
- 理由: 因为目前 Google Sheet 的操作逻辑就是如此;我们的表格就是仿照 Google Sheet 来做的,交互统一可降低学习成本
- 标签: product-ux
- 来源: 2026-08-05 产品讨论 (原话)

## #21 (2026-08-05)
- 场景: 元 skill (全程关注型) 如何保证被激活 — 首个真实使用暴露缺陷
- 决策: 全程关注型 skill 不能依赖按需加载 (AI 不知道要捕获 → 不加载 → 不捕获,循环依赖);用三层冗余激活: 全局 AGENTS.md 常驻注入 (主保障) + description 提前触发 (次保障) + 用户显式关键词兜底
- 理由: 重启后产品讨论表达带理由原则未触发记录;诊断确认 skill 已注册可加载,失败在激活层而非注册层;全局注入是唯一不依赖 AI 判断的保障
- 标签: experience
- 来源: 2026-08-05 实际故障 + 修复 (f0624b9)
