# Decisions 2026-08

## #1 (2026-08-05)
- 场景: C-30 高级 Column Filter 的操作符集合范围 — 全做还是先砍
- 决策: 按 RAW 全做 Text/Number/Date 操作符,而非分批
- 理由: 后端 gt/gte/lt/lte/range 已全部实现,前端加 UI 的成本是边际的;分两次做反而要改两遍 UI 和 e2e
- 标签: engineering

## #2 (2026-08-05)
- 场景: Number/Date 列有了操作符 UI 后,和现有"搜索+多值勾选"的关系
- 决策: 替换 — number/date 列不再以勾选离散值为主要交互,走操作符路径
- 理由: 对 number/date 列勾选离散值本身价值低(用户不会去勾几百个数值);并存/双 tab 会引入"同一列两套条件怎么合并"的复杂语义
- 标签: product-ux

## #3 (2026-08-05)
- 场景: 高级 Column Filter 的菜单布局 — 双 tab 还是单视图
- 决策: 单视图 — 条件规则编辑器与筛选选项列表同屏可见,不做 tab 切换
- 理由: 同一个视图下能同时看到条件与筛选出来的选项列表,操作直觉要更顺
- 标签: product-ux

## #4 (2026-08-05)
- 场景: "多条规则 and/or 联立"的支持边界
- 决策: 同列多规则 + 组内 and/or;跨列保持 AND;不做多级嵌套聚合规则
- 理由: 平铺模型一致(条件数组+组合子);支持最常见需求(同列 or、跨列 and)但明确拒绝多级聚合的复杂度
- 标签: mental-model

## #5 (2026-08-05)
- 场景: 记录决策方法论的 skill 应该存在哪
- 决策: 独立全局 skill (john-methodology),非项目内文件
- 理由: 这是个人品味而非某个项目的特性,跨项目复用价值更高;做成 skill 可按需加载,不占每会话上下文
- 标签: mental-model

## #6 (2026-08-05)
- 场景: 方法论 skill 的归纳(principles)触发方式
- 决策: AI 提议,用户点头后才执行;不自动运行
- 理由: 归纳是提炼个人思维的过程,时机和方向应由用户掌控,避免 AI 自作主张
- 标签: mental-model

## #7 (2026-08-05)
- 场景: 方法论 skill 的捕获方式 — 讨论中何时打断
- 决策: 静默积累,会话自然节点统一列确认卡片;不在讨论中途打断问"要不要记"
- 理由: 不打断沉浸的讨论流;批量确认让用户在完整语境下决定取舍
- 标签: product-ux

## #8 (2026-08-05)
- 场景: 合规/规则类约束 (OT cap 等) 是硬拦截还是仅警示
- 决策: 仅警示 + 留余量供人介入,不硬阻断 — 但附条件: 存在最终业务系统 (外部) 做终审,且本系统规则无法与最终规则完全一致 (信息因素、成本因素) 时才适用
- 理由: 硬拦截与批量审批/事后实算冲突,且阻断正当工作;有外部终审兜底时,本系统只需忠实呈现合规现状 (警示/报表),把决策权和风险留给人和终审系统
- 标签: product-ux
- 来源: ADR-036; 条件由 John 2026-08-05 补充

## #9 (2026-08-05)
- 场景: 刚上线的可配置复杂模型是否保留
- 决策: 若复杂度的产出不体现在用户可见结果上,几天后也敢推翻自己的模型,接受小的公平/精度损失换简单
- 理由: 报销 category→group→priority-chain+pool 模型上线后砍成 account-direct;中间年加入者不按比例 — "换取一个简单得多的模型"
- 标签: mental-model
- 来源: ADR-045

## #13 (2026-08-05)

## #14 (2026-08-05)

- 标签: engineering
- 来源: ADR-062

## #23 (2026-08-06)
- 场景: Clock Time 功能权限设计 — 员工看本人打卡, cc_admin/cc_manager 看本 CC 员工打卡, 是否拆两个 FP (own + managed)

## #24 (2026-08-06)
- 场景: `extra_time_slots.compute_attendance_multiplier_segments` 用 UTC 日期判断跨午夜, SGT 早班 (07:45 = UTC 前一天 23:45) 被误判跨日 → actual OT 恒 0; 单测全绿未暴露, 真实数据端到端验证才发现
- 决策: 业务日归属/跨日判定必须 `dt.astimezone(SGT).date()`, 禁止对 UTC/naive datetime 直接 `.date()`; 相关测试必须含"UTC 跨日但 SGT 同日"用例; review 扫查命令 `rg '\.date\(\)' | grep -v astimezone`
- 理由: 时区错误是**静默的** (算出 0 不报错), 单测也发现不了 — 只能靠硬性约定 + 测试用例 + 扫查命令防复发
- 标签: engineering

## #25 (2026-08-06)
- 场景: C-42 打卡导入全链路 (真实 XLS 文件 → 导入 → OT 申请 → 审批 → 实际 OT 联动计算) — 单测全绿, 真实流程跑一遍才暴露 #24 的时区 bug
- 决策: 涉及计算/管道的新功能, 实现后必须用真实数据走完整业务链路验证 (数据 → 业务操作 → 联动计算), 不能只看单测
- 理由: 单测绿 ≠ 真实数据正确; 真实链路才能暴露跨层/跨模块问题 (如时区、口径、边界)
- 标签: experience

## #26 (2026-08-06)
- 场景: OT 详情页打卡区块字段取舍 — Estimated hours / Variance / e-Cirtix Actual / e-Cirtix Paid 是否保留
- 决策: 移除这四个字段,只保留与加班直接相关的信息: 打卡时间 (Clock Time)、认定加班时间段 (Recognized OT window)、实际加班工时 (Actual hours)
- 理由: "要核对数据自然有报表去核对。在业务层面只用展示与加班相关信息" — 详情页服务业务判断 (这单 OT 实际怎么算), 数据核对是报表的职责
- 标签: product-ux
- 呼应: #13 (每个可见元素必须支持用户的一个决策,否则移除)

## #27 (2026-08-06)

## #37 (2026-08-08)

## #58 (2026-08-26)

- 决策: 不同对象使用不同色相;同一对象内,高关注的未决余量使用深色,进行中的状态使用最亮色,已完成的消耗使用低饱和浅色
